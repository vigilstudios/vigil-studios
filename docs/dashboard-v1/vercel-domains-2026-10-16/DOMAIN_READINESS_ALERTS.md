# Guided progress and verified readiness alerts

The shared guide adds a progress bar and brief encouragement: “Great start!”, “You’re getting closer!”, “Almost there!” and “So close — let’s check your setup!”. Navigation cannot produce a success state. A real verified ownership record shows a green check, “Your part is done!” and the existing ready-for-launch heading, with an explicit explanation that the site is not live yet. A connected domain requires the existing DNS, SSL and expected-site checks; only that state offers Visit my website.

Confetti is decorative, scoped to the success panel, brief and once per browser/domain/milestone. Both a browser preference check and CSS disable it for reduced motion. Reloads, retries, help and record reviews do not intentionally replay it. Ownership verification and live connection have separate celebration keys.

Migration 0048 couples the trusted ownership-readiness update to a staff inbox alert and an idempotent `domain.readiness.notify` job. The queue row is the durable once-per-domain event, so repeated checks, read receipts and deletion of an inbox alert cannot duplicate the event. An outbox insertion failure rolls back readiness; the verifier now propagates that database error for retry instead of returning an uncommitted success. Customers cannot call the private helper or write readiness. Generic staff notification RLS and recipient protection remain unchanged.

The alert names the business and domain, links to the existing admin organization page, and says “domain setup ready for launch review”. It does not approve a review, publish a site or assert a live connection. The email worker revalidates tenant/site/domain/lease identity, current prelaunch readiness and the exact public ownership proof. Email failures do not repeat DNS work. The message is frozen before sending, retries use a stable Resend idempotency key, and uncertain retries stop before the provider’s 24-hour deduplication window expires. Missing configuration never counts as delivery.

Email configuration is an existing operational dependency. The available original-checkout Resend credential returned HTTP 401 during a read-only validation. Production metadata exposes the existing sender/staff/cron secret names but no usable Resend key was available. No credential was created, no Production environment value was changed, and no real customer/staff test email was sent. The in-app staff alert is independent and commits immediately with readiness. Email copies require a valid `RESEND_API_KEY`, verified sender and the existing `STAFF_NOTIFY_EMAIL`/cron configuration; failed jobs can be retried from Admin Jobs once configured.

Release order: validate isolated Preview and migration/RLS; deploy compatible handler/UI first; then apply migration 0048. The migration creates notification/outbox work for any trusted ownership success from the preceding hour, closing the rollout window without editing a domain or website. Email rechecks public proof before delivery. Scar’s DNS, site, reviews, content and contact activation are never QA fixtures and remain protected.

Rollback: remove the new trigger, revoke/remove its private helper and return to the prior code only after canceling undelivered `domain.readiness.notify` jobs. Retain genuine inbox/history rows. The partial unique index is harmless to prior code and can remain. No customer DNS rollback or domain ownership transfer is involved. Validation/release receipts are under `evidence/domain-readiness/`.
