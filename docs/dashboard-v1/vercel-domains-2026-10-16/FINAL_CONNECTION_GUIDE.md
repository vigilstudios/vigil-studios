# Finish all domain records before celebrating

Ownership verification establishes control; it does not finish customer setup. The shared Domain/onboarding guide now waits at 45% after the platform TXT proof passes and explicitly explains that more connection records are required. Existing visible-tab polling continues to read real state. When authorized production activation stores provider requirements, the guide proceeds directly to the first additional record, one record per screen, without repeating provider selection, sign-in or domain-entry questions. A phase-aware v3 navigation key prevents an old completion/check cursor from hiding the newly available records.

Provider TXT challenges are identified as additional connection verification. Multiple TXT values at the same name have explicit separate-record instructions. The already verified platform proof stays in DNS and remains required by the backend verifier; it is not re-entered in the connection guide. Each remaining record has its own Type, Name, Value, copy controls and save acknowledgement, with a link back to Vercel Domains. Navigation never marks a DNS record as verified.

After all records are entered, the final checker waits for required DNS, SSL and HTTPS serving the expected production site. Only a provider-stage, connected domain with DNS, SSL and reachable checks all passing can show 100%, the success screen, the website link and once-per-browser confetti. Reduced-motion handling and the existing connected celebration key are retained. Onboarding can continue while the customer waits, but the button explicitly says that domain setup will be finished later and saves that unfinished state.

Ownership status elsewhere now says Ownership verified rather than suggesting DNS setup is complete. The staff ownership-readiness notification remains a request to review and prepare the next launch stage, not a connection-success notification. No migration, domain reset, customer DNS write, Vercel beta authorization, registrar action, approval change or customer-site deployment is introduced. The existing production approval and artifact gates remain in force; waiting does not trigger publication.

Validation and release receipts are in evidence/final-connection-guide. Browser fixture states use reserved example.test and documentation-only addresses. Positive fixture renders are component behavior tests, not claims of a real purchase, public DNS change or successful customer connection. Shared-dashboard Preview/release checks are separate from customer-site publication. Rollback is a shared-code revert; no DNS or database rollback is required.
