# Actual domain setup from Admin

A signed-in Vigil administrator uses the real customer Domain and onboarding journey: search, save or replace an advisory choice, continue after purchase, edit the guide provider, copy the personal verification record and run the existing ownership checker. The same customer components render; an Admin access banner states that changes persist to the selected account. Old purchase-preview links resolve to the actual guide for a matching saved domain, or the real search flow. Ordinary staff retain read-only discovery. Existing customer owner/manager access remains available.

The service-only advisory handoff function rechecks the real actor as a customer owner/manager or a current staff administrator. Admin choices have explicit staff audit attribution. Saving a choice, opening Vercel and continuing to setup do not establish payment, registrar consent or ownership. No registrar capability, provider credential or DNS permission is added.

Start over with another domain offers a reviewed confirmation for the selected website. Its server action derives the administrator and organization from the session; a single SQL transaction locks and validates the website, current choice version and complete active-domain timestamp snapshot. It refuses production history, a primary/live URL, connected or provider-managed domains, or active production/verification work. It cancels waiting domain work, archives unfinished domain rows, rotates their proof, resolves old readiness alerts, cancels the advisory choice and clears only the project's domain answer. Content, approval and intake state stay intact. A staff audit preserves the affected names and row IDs. No domain registration is canceled and no external DNS is changed.

Released history is retained. A partial unique index still prevents duplicate active names within an organization while allowing a new setup for the same name with a fresh row, verification token and readiness-event identity. In-flight prelaunch DNS checks use the original token and exclude released rows, so old responses cannot revive a reset setup. Stale purchase forms fail the existing intent-version check.

Migration 0049 replaces the handoff function with backward-compatible admin support, adds the service-only reset function and replaces the historical-name unique constraint with an active-name unique index. It performs no customer backfill or automatic resets. Existing code does not call the new reset function, and old handoff callers retain their existing validation, so Git integration migration timing is compatible during deployment. Rollback disables the new UI/actions and revokes the reset RPC after in-flight actions settle; retain archived rows and the active-name index. Do not re-add the former unconditional unique constraint without reconciling historical duplicates.

Validation covers administrator and customer boundaries, direct RPC denial, revoked roles, cross-tenant scope, stale snapshots/choices, worker and production exclusions, atomic reset effects, same-name restart with a fresh proof/event, preservation of approved brief content, and stale DNS responses. Browser QA uses disposable isolated accounts. Scar's actual setup is inspected read-only and must not be reset as a test. Release receipts and screenshots are in evidence/admin-domain-management.
