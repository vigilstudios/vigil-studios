# Native Vigil bookings — November 3, 2026

## Accepted product decisions

The owner prioritized bookings and Lead Hub before Insights/Virtue and deferred a broader security monitor. Standard booking management is included with **Care, Growth and Priority**, subject to the existing entitlement/override system. A service can accept **instant-confirmed appointments or requests requiring approval**. Express sites default to **contact-only**; only explicitly compatible designs advertise the optional Care+ booking component. Eligibility never publishes availability or enables customer communication by itself.

## Shared system

`Onboarding booking needs → service/availability setup → compatible website component → native appointment transaction → Lead Hub calendar and timeline → evidence for Insights/Virtue`.

One native appointment store owns requests, confirmed slots, cancellation, rescheduling and attendance. Website components and dashboard screens consume the same availability and lifecycle endpoints. No parallel appointment list derived from lead labels, booking-link clicks or a third-party iframe callback. Existing external scheduler links stay links and are not imported as verified appointments.

## Surfaces and activation

- **Onboarding:** reuse existing booking goal/features; distinguish standard Vigil appointments, an existing scheduler and complex custom operations. Collect bookable services, instant/request preference and timezone without forcing full calendar setup during checkout. Operating hours only suggest availability; they do not activate slots. Preserve old briefs and custom quotes.
- **Lab:** a registered, brandable booking component and logical booking CTA, backed by the same public contract. Design previews use explicit fictional slots and make no live writes. The component can be placed inline or used as a booking destination.
- **Express:** compatibility belongs to a published variant/version, not an industry name. Contact-only is the default for restaurant and other existing inquiry sections. Show “Optional Vigil bookings · Care and higher” only when a real compatible mount/component exists. Native appointment scheduling does not promise restaurant table allocation, classes, group capacity or deposits.
- **Lead Hub:** Inbox and Bookings share website/lead context. Bookings offers an agenda, approval queue, customer details and lifecycle/attendance actions, with service/resource availability setup. A booking remains separate from a manually selected lead status.
- **Enable:** a live registered website, Care+ entitlement, compatible component, enabled service/resource, reviewed timezone/hours and explicit owner/manager activation are required. Downgrades pause new bookings and retain historical appointments and management access.

## First native release

One business timezone per website; multiple named single-capacity resources; service duration and buffers; weekly availability; date-specific blocked time; lead-time and horizon limits. Public slots are generated in UTC and filtered against local business hours, including daylight-saving days. Booking creates an idempotent request or confirmed appointment atomically. Approval and rescheduling recheck current availability. Confirmed reservations enforce non-overlap in PostgreSQL, including buffers. Requests do not reserve capacity until accepted, and the public receipt says so.

Owner/manager operations are authenticated, tenant-scoped and audited. Public booking uses the registered website identity, strict origin/body validation, distributed abuse limits and server-verified Turnstile. Public callers cannot select a tenant, link an arbitrary existing lead, read other customers or bypass service/plan/availability checks. Guest management uses an unguessable appointment-specific credential stored only as a hash; no authentication based merely on name/email or an appointment UUID.

Public visitors receive a truthful on-screen result and secure management link. Transactional email/reminders require explicit reviewed configuration; testing cannot send to real customers. Google/Microsoft calendar access is a separate optional connector and never reuses Search Console credentials. Until connected, booking availability covers appointments/blocks recorded in Vigil, clearly disclosed during setup. Payments, complex resource pools and autonomous Virtue booking are follow-up capabilities.

## Implementation order and acceptance

1. Native contract, additive schema, Care+ feature rows, tenant/role guards, idempotency, overlap protection and lifecycle events. Test wrong tenant, denied role, Basic, cancelled entitlement, retries/conflicts, DST, stale availability, concurrent reservation/approval/rescheduling and history retention.
2. Public config/slots/booking/guest-management endpoints and one shared branded widget, with no-network Lab preview. Website and dashboard must observe the same state transitions.
3. Lead Hub Bookings workspace plus services/resources/availability setup and lead-detail appointment history. Distinguish requested/confirmed/completed/no-show and preserve source attribution.
4. Lab registration/runtime and compatible Express mount, default contact-only behavior, onboarding import as drafts, catalogue/tier/plan copy and launch-readiness checks. Test previews and exports; preserve archived engine distributions and historical worktrees.
5. Full app/SQL/browser validation and a reviewable PR/preview before production booking rollout. Back up production before any additive schema push; no existing website is enrolled automatically. Test any real pilot only with explicitly configured business services and allowed test recipients.

Operating cost uses the existing application and database; no new fixed subscription or AI runtime is required. Each later email/calendar/payment capability has its own authorization and cost boundary.
